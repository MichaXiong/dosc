# P1.3 项目结构与资源管理

> 阶段 P1 · 讲清 Unity 工程在磁盘上长什么样、哪些该进版本库、资源如何被引用。

## 概念与定位

Unity 工程不是「只有一个 `.exe` 工程文件」，而是一组目录。日常开发几乎只碰 `Assets`，但协作与备份时必须分清：**哪些是源资产，哪些是可再生成的缓存**。

引用关系不靠文件名，而靠每个资产旁的 `.meta` 里的 **GUID**。这是「改名引用还在、只拷文件不拷 meta 就丢引用」的根源。

---

## 根目录职责

```text
MyGame/
├── Assets/           ← 场景、脚本、美术、Prefab（进库）
├── Packages/         ← UPM 依赖清单与内嵌包（进库）
├── ProjectSettings/  ← 标签、输入、画质、Player 等（进库）
├── UserSettings/     ← 本机窗口布局（通常不进库）
├── Library/          ← 导入缓存与编译产物（不进库，可删后重建）
├── Temp/ Logs/ obj/  ← 临时与日志（不进库）
```

| 目录 | 进 Git？ | 说明 |
|------|:--------:|------|
| Assets / Packages / ProjectSettings | 是 | 真正的项目内容与配置 |
| Library / Temp / Logs / obj / UserSettings | 否 | 可再生或纯本机 |

不要把 `Library` 当完整项目拷贝给别人；对方用 Unity 打开工程根目录即可重建。

---

## Assets 组织（基础）

中小型项目常用「自研置顶」结构：

```text
Assets/
├── _Project/
│   ├── Art/          Characters / Environment / UI / VFX
│   ├── Audio/
│   ├── Prefabs/
│   ├── Scenes/
│   ├── Scripts/      Runtime / Editor
│   ├── ScriptableObjects/
│   └── Settings/
├── Plugins/
└── ThirdParty/
```

`_Project` 前缀利用名称排序置顶，避免被示例资源淹没。

### Resources 文件夹

路径中名为 `Resources` 的目录可通过 `Resources.Load` 加载，但会增加打包体积与管理难度。基础阶段知道即可；正式项目更常见 **直接引用** 或后期 **Addressables**。

---

## Packages 与 ProjectSettings

- `Packages/manifest.json`：依赖哪些包及版本；`packages-lock.json` 建议一并提交以锁定解析结果。
- Package Manager 安装的 Input System、Cinemachine、URP 等都会写进 manifest。
- `ProjectSettings` 含 Tags/Layers、输入、Quality、Graphics、Player 等——丢了等于丢半套项目配置。

---

## .meta 与 GUID（常用进阶）

每个资产都有对应 `.meta`（YAML），内含稳定 GUID。场景/Prefab 里存的是 GUID，不是路径字符串。

因此：

1. 资产与 `.meta` 必须一起移动、提交、删除  
2. 在 Unity 的 Project 窗口内改名/移动，引擎会同步 meta  
3. 只复制 `xxx.prefab` 不带 meta → 新 GUID → 原引用变 Missing  

团队建议（Edit → Project Settings → Editor）：

- Version Control：**Visible Meta Files**  
- Asset Serialization：**Force Text**（场景/Prefab 文本化，便于 diff/merge）

---

## 命名与版本控制

| 类型 | 习惯 |
|------|------|
| 场景 / 脚本 / Prefab | PascalCase，脚本类名与文件名一致 |
| 避免 | 空格、中文路径、`New Behaviour Script (1).cs` |

Git 至少忽略 `Library/`、`Temp/`、`Obj/`、`Logs/`、`UserSettings/` 以及本地 IDE 垃圾文件。大体积二进制后续可用 Git LFS（见版本控制相关章节）。

---

## 常见误区

- 把整个工程含 Library 打成压缩包当备份（体积巨大且无必要）  
- 在资源管理器里随便拖文件导致 meta 脱节  
- 依赖 `Resources` 加载一切，后期难做按需下载与包体控制  
- 忽略 ProjectSettings，换机后 Tag/Layer/输入全乱  

---

## 面试题

### Q1. Unity 工程里哪些目录应该进版本库？哪些不应该？为什么？
**参考答案：**  
应进库：`Assets`、`Packages`、`ProjectSettings`（源资产与项目配置）。不应进库：`Library`、`Temp`、`Logs`、`obj`、通常还有 `UserSettings`——它们是缓存/本机设置，可用 Unity 打开工程后重建。提交 `Library` 只会带来巨大体积与无意义冲突。

### Q2. 什么是 `.meta` 与 GUID？为什么「只拷文件不拷 meta」会丢引用？
**参考答案：**  
每个资产旁有 `.meta`，内含稳定 **GUID**。场景、Prefab 里保存的是 GUID 引用，不是文件名。只复制资源文件时 Unity 会生成新 meta/新 GUID，原引用找不到目标，表现为 Missing、洋红材质或脚本丢失。正确做法是资产与 meta 一起移动/提交，并在编辑器内改名。

### Q3. `Resources` 文件夹有什么问题？更推荐怎么管理可加载资源？
**参考答案：**  
名为 `Resources` 的目录可通过 `Resources.Load` 加载，但资源易被打进包、难做精细按需加载与依赖分析。小型原型可用；正式项目更推荐 Inspector 直接引用、Addressables 或自研加载管线，便于包体与热更新控制。

### Q4. 为什么说丢了 `ProjectSettings` 等于丢半个项目配置？
**参考答案：**  
其中包含 Tags/Layers、输入、Quality、Graphics、Player 等全局设置。换机或换人后若没有这些文件，碰撞矩阵、输入轴、包名画质等都会对不上，表现为「代码一样、表现全乱」。
